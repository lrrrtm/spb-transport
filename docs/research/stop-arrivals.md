# Исследование: фактическое прибытие и прохождение участков (T10)

Статус: **пороги откалиброваны на одной выборке** (3 октября 2026, суббота, 12:45–14:15 MSK).
Перед выводами T13–T16 их нужно подтвердить на выборке буднего дня в час пик; что именно
проверить — [`follow-ups.md`](follow-ups.md).

## Алгоритм `stop-events-v1`

1. Для каждого shape выбирается доминирующий stop pattern (больше всего trips) и остановки
   проецируются на shape по порядку с неубывающим `distance_along_m`. Так петли и маршруты
   «туда-обратно» по одной улице получают правильный проход. Остановки дальше
   `STOP_EVENT_STOP_MAX_OFFSET_M` от shape не участвуют.
2. На вход берётся run из T09 — монотонный проход машины по shape — только из `matched`
   наблюдений. Shape задаёт направление: машина, едущая в обратную сторону, принадлежит
   другому shape и не создаёт событий этой остановки.
3. Прогресс заменяется его накопленным максимумом. Поэтому дрожание GPS вокруг остановки не
   создаёт повторного пересечения — каждая остановка даёт не больше одного события на run.
4. Времена входа в геозону, пересечения линии остановки и выхода интерполируются линейно между
   наблюдениями. Интерполяция через пропуск длиннее `STOP_EVENT_MAX_INTERPOLATION_GAP_SECONDS`
   не выполняется.
5. Длительность нахождения: `dwell = выход − вход`; она включает и проезд через зону, поэтому
   остановка определяется по скорости: `stopped = true`, если в зоне есть наблюдение со `speed`
   или со скоростью прогресса между соседними наблюдениями ≤ `STOP_EVENT_STOPPED_MAX_SPEED_MPS`.
   Скорость прогресса нужна, потому что `speed` источника запаздывает: позиция уже не меняется,
   а `speed` ещё ненулевая.
6. Участок между соседними остановками pattern получает `travel_time_s` (линия → линия) и
   `running_time_s` (выход из зоны → вход в зону).

## Параметры

| Параметр | Значение | Обоснование (выборка 2026-10-03) |
|---|---:|---|
| `STOP_EVENT_STOP_MAX_OFFSET_M` | 40 | Остановки лежат на shape: p99 расстояния 9,5 м; при 40 м не проецируется 0,0% |
| `STOP_EVENT_ZONE_BEFORE_M` | 40 | Доля `speed=0` выше фона (≈15%) на интервале [−50, +50) м от линии остановки; до линии фон начинается раньше из-за очередей и светофоров |
| `STOP_EVENT_ZONE_AFTER_M` | 40 | Максимум стоящих машин на [+10, +30) м: транспорт останавливается после точки остановки GTFS; [+40, +50) ещё выше фона |
| `STOP_EVENT_MAX_INTERPOLATION_GAP_SECONDS` | 120 | Интервал интерполяции пересечения: p50 10 с, p99 65 с; интервалов > 120 с 0,3% |
| `STOP_EVENT_STOPPED_MAX_SPEED_MPS` | 0,5 | `speed` в м/с; скорость прогресса в зоне ≤ 0,5 м/с у 85% посещений, дальше распределение почти плоское |

Проверки после новой калибровки:

- доля `interpolated` и `departure_only` среди событий;
- доля участков с `max_gap_s` выше порога T13;
- dwell при `stopped=true` заметно больше, чем при `stopped=false`;
- ручная проверка 20–30 случайных runs на карте (позиции, линии остановок, события).

Изменение формул, а не только значений параметров, требует новой `ALGORITHM_VERSION`.

## Известные ограничения

- Остановка, которую run начал уже за её зоной, не получает события.
- Для начальной остановки run часто известен только `departure_time` (`departure_only`).
- Используется один pattern на shape; trips с другим набором остановок на том же shape
  (укороченные рейсы) получают события только для общих остановок доминирующего pattern.
- Линейная интерполяция занижает dwell, если машина остановилась между двумя редкими
  наблюдениями вне зоны.

## Результаты: выборка 2026-10-03

Static feed `e1271210…bd3f0`, matcher с параметрами из [`route-matching.md`](route-matching.md),
в событиях участвуют только `matched` наблюдения.

**Stop patterns.** У каждого из 1 045 shape ровно один stop pattern (все trips shape проходят
одни и те же остановки), поэтому выбор доминирующего pattern ничего не теряет. Остановки лежат
на линии shape (p99 9,5 м). Медиана расстояния между остановками 490 м, p1 118 м; зоны 80 м
перекрываются у 0,6% пар.

**Где стоит транспорт.** Доля `speed=0` среди наблюдений рядом с остановкой: фон 12–16% на
расстоянии 60–150 м, 20–25% на [−50, +10), максимум 35–37% на [+10, +30), 24–25% на [+30, +50).
Отсюда несимметричный характер остановки (останавливаются после точки GTFS) и зона ±40 м.

**События** (7 940 прогонов, 82 224 события):

| Показатель | Значение |
|---|---|
| method | observed 91,6%, interpolated 5,3%, departure_only 3,1% |
| stopped | true 78,5%, false 16,0%, неизвестно 5,5% |
| dwell, медиана | 28,6 с при stopped=true; 17,9 с при stopped=false (проезд зоны 80 м) |
| интервал интерполяции | p50 10 с, p90 19 с, p99 65 с |

Первая версия признака `stopped` (dwell ≥ 10 с) отмечала 87% событий и не различала проезд и
остановку: dwell проезда через зону сам по себе 15–25 с. Признак по reported `speed=0` давал 32%:
`speed` источника запаздывает. Принят признак по скорости прогресса или `speed`.

**Участки** (75 431): `travel_time` известно у 97,0%, `running_time` — у 99,9%; travel_time
p50 92 с, p95 226 с; средняя скорость p50 5,2 м/с (19 км/ч), p95 11,2 м/с; максимальный интервал
наблюдений на участке p50 13 с, p95 45 с, p99 86 с.

Ограничение данных: координаты источника привязаны к линии маршрута, поэтому стоящая машина
видна как неизменный прогресс. Повторы последней позиции источником разобраны в разделе
«Будние выборки 2026-10-07».

Воспроизвести:

```shell
set -a; source <(grep -E '^(ROUTE_MATCH|STOP_EVENT)_' .env.example); set +a
uv run python scripts/research/analyze_stop_events_sample.py \
    data/research/route-matching/20261003T094520427201Z
```

## Будние выборки 2026-10-07

Те же выборки, что в [`route-matching.md`](route-matching.md#проверка-на-будних-выборках-2026-10-07):
будний день 14:08–15:38 MSK и вечерний пик 17:30–19:00 MSK. Static feed `e5eb3422…f5753`, у
всех 1 045 shape по одному stop pattern, как и раньше. Цифры ниже получены при
`max_backtrack` = 30; с 100 м число событий в пик то же (100 309 → 100 264).

**Зона перед остановкой.** Доля `speed=0` по расстоянию до линии остановки:

| Интервал, м | Суббота | Будни, день | Будни, пик |
|---:|---:|---:|---:|
| [−100, −70) | 15–16% | 15–16% | 15–18% |
| [−70, −50) | 17–19% | 20–22% | 19% |
| [−50, −40) | 22% | 26% | 21% |
| [−40, 0) | 21–25% | 21–24% | 20–26% |
| [+10, +30) | 35–37% | 34–35% | 34–35% |
| [+40, +60) | 17–24% | 19–21% | 17–20% |
| фон [+90, +150) | 7–15% | 8–13% | 9–14% |

Очередей перед остановкой в пик не видно: подъём над фоном начинается там же, на [−70, −50) м,
и не выше субботнего. В будний день подъём на [−70, −40) м чуть сильнее (20–26%), но он меньше
пика после линии и начинается не раньше −70 м. `STOP_EVENT_ZONE_BEFORE_M` = 40 оставлен: расширение
зоны добавило бы в dwell проезд, а не остановку.

**События:**

| Показатель | Суббота | Будни, день | Будни, пик |
|---|---:|---:|---:|
| событий (прогонов) | 82 224 (7 940) | 105 561 (9 975) | 100 309 (10 905) |
| observed / interpolated / departure_only | 91,6 / 5,3 / 3,1% | 91,8 / 5,0 / 3,2% | 91,6 / 5,1 / 3,4% |
| stopped true / false / неизвестно | 78,5 / 16,0 / 5,5% | 80,4 / 14,4 / 5,2% | 81,2 / 13,5 / 5,3% |
| dwell p50 при stopped=true / false, с | 28,6 / 17,9 | 29,2 / 17,5 | 30,4 / 17,3 |
| dwell p95 при stopped=true, с | 65 | 67 | 77 |
| travel_time участка p50 / p95, с | 92 / 226 | 94 / 224 | 100 / 290 |
| скорость на участке p50, м/с | 5,2 | 5,1 | 4,8 |

Признак `stopped` работает и в будни: dwell при остановке в 1,6–1,8 раза больше, чем при проезде. В пик
dwell и время на участках длиннее, особенно хвост (p95 travel_time 290 с против 226 с).

**Повтор последней позиции.** Источник часто присылает ту же запись машины с новым
`source_timestamp`: координаты, `speed` и `bearing` совпадают. Серии из ≥ 3 таких наблюдений со
`speed > 0` содержат 25–28% всех наблюдений: 16–17% у остановок (ближе 40 м) и 9–12% между ними
(`analyze_matcher_edge_cases.py` §3). Медиана серии — 4 наблюдения, 30 с, `speed` в серии
p50 2,8 м/с. Что делала машина, видно по следующей отличающейся позиции: средняя скорость от первой
копии до неё — медиана 0,9 м/с, в 60% серий меньше половины заявленной `speed` (у обычных пар
соседних позиций — в 14%). Значит, чаще всего машина стояла, а запаздывает поле `speed`; реже
позиция действительно устарела, пока машина ехала.

Проверен фильтр (не принят): копии отбрасываются, если средняя скорость до следующей позиции не
меньше половины заявленной. Доля `stopped=true` падает с 78–81% до 50–53%, но разница dwell
«остановка / проезд» тоже сокращается (29,8 / 21,3 с в субботу вместо 28,6 / 17,9 с): часть
отброшенных серий — настоящие короткие остановки. Без эталона выбрать порог нельзя, а времена
событий и участков от фильтра почти не меняются (travel_time p50 92,1 → 91,8 с). Поэтому оставлен
`stop-events-v1`, а `stopped=true` читается как верхняя оценка: «машина стояла или источник не
обновлял позицию»; нижняя оценка — около 50% событий.
