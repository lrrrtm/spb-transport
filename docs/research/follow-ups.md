# Доработки по результатам исследования и нужные выборки

Документ фиксирует, что в T09/T10 проверено только частично и какие данные нужны, чтобы это
закрыть. Пункты упорядочены по важности; рядом с каждым — выборка из раздела «Выборки».

## Выборки

| ID | Что собрать | Как | Зачем |
|---|---|---|---|
| **A** | Будний день, час пик (8:00–10:00 или 17:00–19:00 MSK), 90 минут | `collect_route_matching_sample.py --duration-minutes 90` | Подтвердить пороги T09/T10, полученные на субботе |
| **B** | Будний день, дневное время (12:00–15:00 MSK), 90 минут | то же | Отделить эффект часа пик от эффекта будней; по желанию |
| **C** | Полные сутки через Docker-пайплайн (collector → Kafka → `spark-position-stream` → HDFS), затем `spark-route-matching` и `spark-stop-events` за этот день | `docker compose up -d`, через сутки — команды из `docs/configuration.md` | Проверить jobs на кластере, производительность, границу суток UTC |

Выборки A/B анализируются без Docker:

```shell
set -a; source <(grep -E '^(ROUTE_MATCH|STOP_EVENT)_' .env.example); set +a
uv run python scripts/research/analyze_route_matching_sample.py --with-matcher data/research/route-matching/<run>
uv run python scripts/research/analyze_stop_events_sample.py data/research/route-matching/<run>
```

Отчёты сохраняются рядом с выборкой (`report.md`, `stop-events-report.md`); выводы переносятся в
`route-matching.md` / `stop-arrivals.md`, сами выборки в git не попадают.

## T09: route/shape matching

1. **Подтвердить пороги на будний час пик** — выборка **A**.
   Сравнить с субботой (`route-matching.md`, «Результаты»): §3 отклонение GPS, §5 неоднозначность
   вариантов, §8 доли `match_status`, длина прогонов, границы прогонов.
   Пороги остаются, если `matched` ≥ 90%, `low_confidence` ≤ 3%, смен варианта в середине и
   разрывов прогона на тысячу прогонов не больше, чем в субботу. Иначе — повторить подбор из
   `route-matching.md` (таблица вариантов) и обновить `.env.example`.
2. **Прогон job на кластере** — выборка **C**.
   `route_match_batch.py` проверен на локальном Spark (`make test-spark`), но не в Docker на
   реальном дне. Записать в `route-matching.md`: время job за сутки, число позиций, счётчики
   `match_status` из лога. Ориентир: matcher обрабатывает ≈ 15 тыс. позиций/с на одно ядро.
3. **Граница суток** — выборка **C**.
   Трек не переходит через полночь UTC (03:00 MSK). Посчитать, сколько машин имеют наблюдения в
   02:30–03:30 MSK; если заметная доля — читать хвост предыдущего дня.
4. **Разрывы прогона после скачка позиции** — выборки **A** или текущая.
   817 из 4 337 границ прогонов в субботу — разрыв на том же shape в середине маршрута после 1–7
   наблюдений `off_route` и прогресса быстрее 30 м/с. Посмотреть 20 случаев на карте: если это
   скачок GPS, а машина фактически ехала дальше, — разрешить продолжение прохода после
   `off_route`-участка с учётом времени (новая `ALGORITHM_VERSION`). Влияет только на покрытие T10.
5. **Смены варианта в середине маршрута** — выборка **A**.
   443 случая в субботу. Отделить укороченные рейсы (реальный разворот) от ошибок по 20 случаям на
   карте. Если ошибок много — поднять `ROUTE_MATCH_SWITCH_COST`.
