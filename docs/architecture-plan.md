# План проекта

Система собирает данные о движении общественного транспорта Санкт-Петербурга из открытого
API (static GTFS и GTFS Realtime), хранит историю и считает по ней метрики: узкие участки
маршрутов, прогноз прибытия, аномалии и профили маршрутов. Здесь описано, как устроена
система, где лежат данные и в каком порядке мы делаем задачи.

## Источник данных

Static GTFS скачивается архивом:
`https://transport.orgp.spb.ru/Portal/transport/internalapi/gtfs/feed.zip`.

Realtime-методы находятся по адресу
`https://transport.orgp.spb.ru/Portal/transport/internalapi/gtfs/realtime`:

- `/vehicle` — текущие позиции всех машин;
- `/vehicletrips?vehicleIDs=...` — прогнозы прибытия для указанных машин (параметр обязателен);
- `/stopforecast` — есть, но мы его не проверяли и пока не используем.

Что реально приходит в `/vehicle`: `vehicle.id`, `trip.route_id`, координаты, `bearing`,
`speed`, `timestamp`, `vehicle.label` и `vehicle.license_plate`. В `/vehicletrips` — машина,
маршрут и список `stop_time_update` с `stop_id` и `arrival.time`.

Чего в источнике нет: `trip_id`, `stop_sequence`, `arrival.delay`, `departure.*`. Поэтому
наблюдение нельзя напрямую привязать к рейсу из расписания, а порядок элементов в прогнозе
мы храним как `forecast_rank` и не выдаём его за `stop_sequence`.

Что важно учитывать при обработке:

- одна и та же позиция приходит при нескольких опросах подряд, дедупликация — минимум по
  `(vehicle_id, timestamp)`;
- частота опроса API не равна частоте обновления GPS;
- `speed = 0` — нормальное значение, а не пропуск;
- пустой список прогнозов — тоже нормальный ответ;
- ошибки 5xx, таймауты и битый protobuf не должны останавливать коллектор.

Если источник поменяет формат, сначала разбираемся с новым ответом на выборке, потом меняем
модели, тестовые данные и документацию.

## Как устроена система

```text
Static GTFS feed.zip
        │
        ▼
GTFS ingestion ──► HDFS raw/static/version=...
        │
        ├────────► HDFS processed/static/version=...
        └────────► Cassandra: маршруты и остановки

/vehicle + /vehicletrips
        │
        ▼
Collector ──► Kafka: raw-ответы, позиции, ETA
                         │
                         ▼
                Spark Structured Streaming
                    │            │
                    │            └──► Cassandra: текущее состояние и история
                    ▼
              HDFS bronze/silver
                    │
                    ▼
              Spark batch: matching, события, метрики, модели
                    │
                    ├──► HDFS gold
                    └──► Cassandra: аналитические таблицы
                                      │
                                      ▼
                               FastAPI ──► React
```

**Collector** опрашивает `/vehicle`, затем порциями запрашивает `/vehicletrips` для активных
машин, декодирует protobuf и публикует события в Kafka. В нём собраны таймауты, повторы с
backoff и настройки TLS. Ничего аналитического коллектор не считает.

**Static GTFS** загружается отдельным разовым job: архив сохраняется как есть, проверяется,
получает версию и раскладывается в Parquet (маршруты, остановки, shapes, последовательности
остановок). Справочники для интерфейса публикуются в Cassandra.

**Kafka** — буфер между коллектором и Spark. Три топика: `vehicle-position.v1`,
`vehicle-eta.v1` и `gtfs-raw-response.v1`. Формат — JSON с версией схемы, модели описаны на
Pydantic в `packages/contracts`. Schema Registry пока не нужен.

**Spark** работает в двух режимах. Стримы читают Kafka, чистят и дедуплицируют данные, пишут
историю в HDFS и текущее состояние в Cassandra. Batch-задачи считают всё тяжёлое:
сопоставление с маршрутами, события на остановках, метрики участков, признаки и модели.

**HDFS (Parquet)** — основное хранилище истории. Из него можно заново пересчитать всё
остальное.

**Cassandra** хранит только готовые ответы на известные запросы API. Произвольных запросов и
join'ов к ней нет.

**FastAPI** отдаёт данные из Cassandra: только чтение, пагинация, ограничение диапазонов,
`/health` и `/ready`. Тяжёлых расчётов в обработчиках запросов нет.

**Веб-интерфейс** — React, TypeScript, MUI, MapLibre и Plotly: карта транспорта, узкие
участки, карточка маршрута, сравнение ETA, интервалы, аномалии и кластеры маршрутов.

## Где лежат данные

Сырые данные и bronze в HDFS:

```text
/raw/static_gtfs/ingest_date=YYYY-MM-DD/version=<sha256>/feed.zip
/processed/static_gtfs/version=<sha256>/{routes,stops,trips,shapes}/
/raw/realtime/source=vehicle/ingest_date=YYYY-MM-DD/hour=HH/
/raw/realtime/source=vehicletrips/ingest_date=YYYY-MM-DD/hour=HH/
/bronze/vehicle_positions/event_date=YYYY-MM-DD/hour=HH/
/bronze/vehicle_eta_snapshots/event_date=YYYY-MM-DD/hour=HH/
```

Raw-ответ хранится вместе с HTTP-статусом, временем запроса, контрольной суммой и ошибкой
декодирования, если она была. Повторы в raw допустимы, дедупликация начинается дальше.

Silver — очищенные и обогащённые данные:

```text
/silver/vehicle_positions/event_date=...
/silver/vehicle_route_matches/event_date=...
/silver/eta_predictions/event_date=...
/silver/stop_arrival_events/event_date=...
/silver/segment_traversals/service_date=...
/silver/data_quality_issues/event_date=...
```

Gold — агрегаты и наборы для моделей:

```text
/gold/segment_metrics/window=.../service_date=...
/gold/route_daily_features/service_date=...
/gold/headway_metrics/service_date=...
/gold/anomalies/type=.../event_date=...
/gold/eta_training_dataset/dataset_version=...
/gold/eta_evaluations/model_version=...
/gold/route_clusters/model_version=...
```

У каждого производного набора есть версия алгоритма или модели, чтобы результаты разных
версий не смешивались.

В Cassandra на старте планируем такие таблицы: последние позиции по машине и по маршруту,
история позиций и ETA по дням, метрики участков, сравнение ETA, аномалии, признаки и
кластеры маршрутов, справочники маршрутов и остановок. Партиции ограничены по времени, TTL —
только для короткоживущих данных.

## Конфигурация и надёжность

Все адреса, интервалы опроса, размер порции `vehicleIDs`, таймауты, повторы, адреса Kafka,
HDFS и Cassandra, пути checkpoint'ов, retention и пороги аналитики задаются через переменные
окружения. Обязательная настройка без значения останавливает запуск с понятной ошибкой.
Пример значений — в `.env.example`, сам `.env` в репозиторий не попадает.

Проверка TLS-сертификата включена по умолчанию. Отключить её можно только явно, через
`GTFS_TLS_VERIFY=false`, и тогда коллектор пишет предупреждение при старте.

Повторы запросов ограничены и идут с экспоненциальной задержкой. Если все попытки
исчерпаны, ошибка цикла пишется в лог, а следующий цикл стартует как обычно.

## Аналитика

**Узкие участки.** Считаем по направленным участкам между соседними остановками после
уверенного сопоставления с маршрутом: медиана и квантили времени, скорость, разброс, доля
остановок, отношение часа пик к обычному времени, число наблюдений.

**Прогноз прибытия.** Начинаем с простой модели на исторических медианах по участкам с
учётом часа, дня недели и текущей скорости. Сравниваем с официальным прогнозом на одних и
тех же случаях: MAE, медианная ошибка, ошибка по горизонту, покрытие.

**Замедление.** Целевая переменная — превысит ли время следующего участка исторический p90.
Обучение и проверка разделены по времени.

**Кластеры маршрутов.** Признаки: скорость, стабильность времени на участках, регулярность
интервалов, доля стоянок, частота аномалий.

**Аномалии.** Пачки и большие интервалы считаем по прогрессу вдоль маршрута, а не по прямому
расстоянию. Длительная стоянка — только по серии наблюдений. Отдельно ищем скачки GPS,
пропавшие машины и нестандартное время на участке.

## Этапы и задачи

Работа идёт в четыре этапа.

1. Сбор и сохранение данных: коллектор, static GTFS, Kafka, архив в HDFS, стримы.
2. Обогащение и выдача: сопоставление с маршрутами, события на остановках, Cassandra, API и
   карта.
3. Аналитика: метрики участков, аномалии, ETA, классификация замедления, кластеры.
4. Завершение: аналитические экраны, тесты отказов, наблюдаемость, демо и отчёт.

## Когда задача считается готовой

- работает в своей части цепочки и описана в документации;
- не использует поля, которых нет в источнике;
- повторная обработка не создаёт дублей;
- `speed = 0`, пустой ETA, повторный timestamp и битый ответ покрыты тестами, где это
  применимо;
- для Spark-задачи описаны вход, выход, партиционирование и checkpoint'ы;
- у таблицы Cassandra есть конкретный запрос, под который она сделана;
- у модели есть baseline, разбиение по времени и метрики;
- `make check` проходит локально и в CI.

## Что сознательно не делаем

PostgreSQL, Airflow, Kubernetes, Schema Registry, отдельный сервис на каждую аналитическую
задачу, нейросетевой ETA и онлайн-обучение. Не пытаемся точно восстановить рейс без
`trip_id` и не используем `/stopforecast`, пока не разберёмся с его данными. Вернёмся к
этому, если появится реальная необходимость.
