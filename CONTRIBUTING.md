# Правила разработки

## Ветки и merge requests

- Одна ветка и один MR соответствуют одной задаче backlog.
- Имя ветки: `<task-id>-<short-description>`, например `t02-vehicle-ingestion`.
- MR должен давать законченный инженерный результат, но не смешивать collector, Spark, API и UI без необходимости.
- Изменения общих контрактов проверяет разработчик второй затронутой области.
- Автор не одобряет собственный MR.

## Владение областями

- Developer A: `apps/collector`, realtime semantics, ETA и транспортные аномалии.
- Developer B: `apps/api`, `apps/web`, static GTFS и Cassandra serving schema.
- Developer C: `pipelines/spark`, HDFS layout и аналитические jobs.
- `packages/contracts`, `infra` и `docs/architecture` требуют cross-review.

Это организационное владение, а не запрет на совместную работу.

## Коммиты

- Коммит отражает естественный проверяемый шаг: контракт, рабочая логика, тесты или документация.
- Не следует искусственно дробить изменение ради количества коммитов.
- Зависимости и Python-окружение управляются только через `uv`; `pip install` вручную не используется.
- Перед push выполняются `make install` и `make check`.

## Изменение контракта данных

Если API возвращает структуру, отличающуюся от подтверждённой:

1. сохранить обезличенный raw fixture;
2. описать наблюдение в `docs/research/`;
3. обновить ADR или data-contract документацию;
4. обновить DTO и compatibility tests отдельным MR;
5. только затем использовать новое поле в приложениях или аналитике.
